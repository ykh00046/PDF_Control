# PDF Open-with-Password + Remove Protection — Plan

> **Status**: ✅ Approved
> **PDCA**: pdf-open-decrypt
> **Author**: Claude (bkit)
> **Created**: 2026-06-08
> **선행**: pdf-encryption (저장 시 암호화는 완료, 그 *짝*인 열기/해제가 본 사이클)

---

## 1. 배경 / 문제

선행 `pdf-encryption` 사이클로 **암호화 저장**(AES-256 + 권한)은 출시됐으나, 그렇게 만든
파일을 **다시 열 수 없고**, 한 번 보호한 파일의 **보호를 해제**할 수도 없다.

- 현재 `open_document = fitz.open(path)`는 암호화 PDF에 대해 예외 없이 *성공*하지만
  `doc.needs_pass`가 참이라 페이지에 접근하면 깨진다 → 사실상 암호화 파일을 못 연다.
- 즉 출시한 기능이 **단방향(쓰기 전용)**이라 반쪽 상태.

## 2. 목표 (In Scope)

1. **암호화 PDF 열기**: 열기 시 암호 필요를 감지 → 비밀번호 프롬프트 → 인증.
   오답 시 재시도, 취소 가능. 드래그앤드롭 경로도 동일.
2. **보호 해제(복호화 저장)**: 현재 열린(인증된) 암호화 문서를 **암호 없는 평문 PDF로
   다른 이름 저장**. File 메뉴 전용 액션으로 의도를 명확히 노출.
3. **편집/프리뷰/저장 일관성**: 암호화 파일을 연 뒤에도 프리뷰 렌더·편집·저장이
   기존과 동일하게 동작(소스 재오픈 경로에 암호 전달).
4. **100% 하위 호환**: 평문 PDF 동작 불변. 신규 파라미터는 전부 keyword-optional.

## 3. 비목표 (Out of Scope)

- 비밀번호 변경(재암호화는 기존 "암호화하여 저장"으로 가능하므로 별도 액션 불필요).
- 인증서/공개키 기반 암호화, 권한별 부분 잠금 해제.
- 비밀번호 강도 측정, 키체인/자격증명 저장.
- 빈 사용자 암호 + 소유자 암호만 있는(프롬프트 없이 열리는) 파일의 자동 "암호화됨" 표시
  — known limitation으로 문서화.

## 4. 사용자 시나리오

1. 사용자가 암호화 PDF를 연다 → 비밀번호 입력 다이얼로그 → 정답 입력 → 정상 표시.
2. 오답 → "비밀번호가 올바르지 않습니다" 안내 후 재입력. 취소 → 열기 중단.
3. 보호된 문서를 열고 File → **"보호 해제(복호화)..."** → 평문 사본 저장 → 상태바 안내.
4. 보호된 문서를 편집(텍스트 교체 등) 후 일반 "다른 이름으로 저장" → 평문으로 저장(자연 복호화),
   또는 "암호화하여 저장"으로 재암호화.

## 5. 수용 기준 (Acceptance)

- [ ] 암호 없이 암호화 PDF 열기 → `PasswordRequired` 발생, 프롬프트 표시.
- [ ] 정답 입력 → 페이지 접근 가능, 예외 없음.
- [ ] 오답 입력 → `IncorrectPassword`, 재시도 루프.
- [ ] 암호화 문서 → "보호 해제" → 결과 파일 `needs_pass == False`, 내용 보존.
- [ ] 암호화 문서 편집 후 일반 저장 → 평문 + 편집 반영.
- [ ] 평문 PDF 열기/저장 회귀 0 (기존 191 테스트 유지).
- [ ] mypy strict 게이트 유지, i18n en/ko 동기.

## 6. 리스크

| 리스크 | 완화 |
|---|---|
| 소스 재오픈 경로(저장/프리뷰)가 암호를 몰라 깨짐 | 세션이 `_password` 보관 → 모든 재오픈 경로에 스레딩 |
| 프리뷰 워커(별도 프로세스)에 암호 전달 = 디스크 평문 노출 | job JSON은 임시 디렉터리에 쓰고 렌더 직후 삭제. 암호화 세션일 때만 포함. 문서화된 트레이드오프 |
| 컨트롤러에 Qt 다이얼로그 혼입(레이어 침범) | 프롬프트 루프는 UI(file_handlers)에 두고, 컨트롤러는 예외만 전파 |
